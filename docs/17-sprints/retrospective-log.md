### Sprint 01 retrospective — 2026-08-01

**What surprised us:** "Verified locally, all green" was not the same claim as "CI-ready." Local
`pnpm lint`/`typecheck`/`test`/`build` all passed clean, and the sprint's Definition of Done was
checked off on that basis — but the *first* real run of `pr.yml` against GitHub's own runner failed
twice in a row on things local runs never hit: a missing `packageManager` pin (Corepack has no local
fallback to guess from on a fresh CI machine, unlike a dev machine with pnpm already installed
globally) and an eslint rule flagging Next.js's own autogenerated `next-env.d.ts` (only regenerated
with the exact triple-slash-reference shape that trips the rule once `next build`/`next dev` has
actually run with typed routes enabled — a local state that had quietly built up over the sprint
without ever being lint-checked against a truly fresh checkout). Separately: GitHub's free tier does
not support branch protection on private repositories at all — a real product-tier constraint neither
[repository-setup.md](repository-setup.md) nor any earlier phase had surfaced, since no prior phase
priced out the actual GitHub plan being used.

**What we're changing:** A sprint's "tests pass in CI" Definition-of-Done box is not checked until a
real pull request has actually been opened and `pr.yml` has actually run against it and passed — not
inferred from "passes locally" plus the workflow file existing. This is exactly
[repository-setup.md §4](repository-setup.md#4-reproducibility-from-a-clean-checkout)'s already-stated
principle ("works in CI and works from clean are the same claim, not two claims that could silently
drift apart"); Sprint 01 stated the principle correctly but didn't actually practice it until its
last day, closing the CI checkbox on inference rather than evidence for most of the sprint. Every
sprint from Sprint 02 onward opens at least one real PR before claiming that box, full stop.

**Did the last change help?** N/A — this is the first retrospective; nothing to check yet. Sprint
02's retrospective is where this gets checked against reality.

## Why only real entries land here

Per this phase's rule, a retrospective must change something concrete or it is cancelled — logging
*only* the retrospectives that produced a real change (never a blank "nothing to report" filler
entry) is what keeps this document a useful record of this project's actual process evolution rather
than a diary.
